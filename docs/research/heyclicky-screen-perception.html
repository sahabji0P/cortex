How HeyClicky
sees the screen

It doesn't watch pixels and guess. It reads the accessibility tree of a single named window, acts by element index in the background, then re-reads to prove the action landed — and paints a synthetic pointer overlay so a human can watch. This is a teardown of the mechanism, read straight out of HeyClicky 1.0.42's own bundled skill, and what it means for the Cortex screen plane.

source · HeyClicky.app 1.0.42 (51) engine · Codex + cua-driver MCP helper · ClickyComputerUseRuntime upstream · trycua/cua · MIT

The short answer

Five facts, then the detail

1

It reads structure, not pixels. The primary "sight" is the macOS accessibility (AX) tree of one window, returned as marked-up text with clickable element_index handles — a screenshot rides along only to disambiguate.

2

The pointer you saw is an overlay, not your cursor. A triangle glides along a Bézier path to each target and ring-ripples on landing. It's a visual for demos — the real actions are injected in the background and never move your mouse.

3

Snapshot → act → re-snapshot, every time. Every action is bracketed by a fresh window read. The "after" read is the proof the click actually did something.

4

Your foreground app never changes. The entire product exists to drive a background app while you keep typing — no focus steal, no Space switch, no window raise.

5

"Recording" is real upstream, but switched off here. Cua can record full action trajectories; HeyClicky's shipped build deliberately does not expose recording/replay as a callable tool.

The mechanism

The canonical loop

One invariant governs everything: every action is bracketed by a fresh get_window_state(pid, window_id). Click a phase to expand it.

01Before

Snapshot

Read the AX tree of the exact window. This assigns the element indices you're about to use.

02Act

Element action

Click / type / scroll by element_index — dispatched at the AX layer, in the background.

03After

Re-snapshot & verify

Read again. A changed tree is the evidence the action fired. No change ⇒ silent no-op — say so.

What a "look" actually returns

Three ways to see — capture_mode

A single knob decides whether a snapshot returns structure, pixels, or both. The default (som — "set of marks") is why element clicks work on the very first look.

Tree + screenshot

The AX tree says what's clickable and hands back element_index handles; the screenshot disambiguates when labels repeat or are empty. Preferred addressing: element_index (pixels are diagnostic only in HeyClicky).

get_window_state({pid:844, window_id:10725})
// → tree_markdown: "[7] AXTextField …
//                  [14] AXButton 'Save' …"
// → screenshot: <PNG>

Why it's the default

Element-indexed clicks land on the first snapshot with visual confirmation. The other two modes are opt-in when the caller explicitly wants only one half of the work.

Tree only — no PNG

Pure structure. Fastest, cheapest, fully deterministic addressing by element_index. No visual to reason over.

set_config({capture_mode:"ax"})
// snapshots now return tree_markdown, no screenshot

PNG only — no tree

Read-only visual inspection. The model reasons purely from pixels — grounding is slower on dense text because the vision pipeline downsamples aggressively. In HeyClicky, coordinate clicks are blocked, so this is for looking, not driving. (Renamed from screenshot; the old value still decodes.)

The rule the whole product is built on

The no-foreground contract

Quoting the skill: "The user's frontmost app MUST NOT change. Users pay for the right to keep typing in their editor while an agent drives another app in the background."

NEVER

No open (any form routes through LaunchServices & activates), no osascript … activate, no cliclick (warps your real cursor), no tab-switch shortcuts (visible flip). Even ⌘L is banned — a "focus here" shortcut is a focus-steal.

INSTEAD

Launch via idempotent launch_app({bundle_id}) with a FocusRestoreGuard that clobbers any activation back. Drive backgrounded windows by element index. Prefer windows over tabs — each window has its own AX tree and can be inspected without activating.

The "recording" feature, precisely

What recording is — and why it's dark in this build

Upstream, it's real

Cua's driver both paints and records the agent cursor, and standalone Cua can capture full trajectories: action inputs, post-action snapshots, screenshots, and timing metadata into per-turn folders — for demos, regression diffs, or training data. That's the "it records the screen with the cursor" idea you spotted.

In HeyClicky 1.0.42, it's off

The shipped RECORDING.md is explicit: "HeyClicky's default managed runtime does not expose Computer Use recording or replay tools." The only shipped loop is snapshot → act → re-snapshot. Recording tools aren't registered — capability is gated at the tool manifest, not just by prompt wording.

NUANCE

So the visible synthetic cursor overlay (default-on, the pointer you saw gliding) and full trajectory recording/replay (off) are two different things. What "just shipped" as a visible, toggleable pointer is the overlay; the record-and-replay machinery exists in the Cua lineage but is intentionally unregistered in the current signed build.

Why this matters for us

Read-across to the Cortex screen plane

This corroborates the direction already sketched in cortex-local-execution-adapters.html: the screen is a separate native capability plane, not a flag on a provider adapter. Concrete lessons:

adoptStructure-first perception

Default to the AX tree + element indices; keep raw-pixel/vision as an opt-in fallback. It's cheaper, deterministic, and dodges the pixel-grounding correction loops.

adoptSnapshot-verify invariant

Bracket every action with before/after reads and treat "tree unchanged" as failure. Cheap honesty; maps cleanly onto a tool.completed{is_error} event.

adoptCapability gated at the manifest

Don't rely on prompt wording to withhold dangerous tools. Register only the safe subset — exactly how recording/replay and pixel clicks are kept out here.

adoptA signed native host owns TCC

One signed macOS helper owns Accessibility + Screen Recording grants and the overlay; the FastAPI core stays provider-neutral and never touches pixels directly.

brandIt's a capability, not an "agent"

HeyClicky frames one assistant privately invoking a computer-use capability. Same posture we want: a single entity that does the work — the word "agent" never surfaces.

re-testDon't assume the entitlement transfers

Permission inheritance, background-event behavior, Cua licensing and code-signing must be validated independently for a Cortex bundle. The teardown proves what Clicky ships, not that we may copy it.
