Recommended shape

Start with the smallest honest integration: one configured execution engine, one trusted workspace, one mutating run at a time.

decision / 01

Personal-use MVP

Launch Codex non-interactively behind a narrow supervisor.

Use codex exec --json through ordinary async pipes—not a PTY—with an explicit -C workspace, workspace-write sandbox, network off, and --ask-for-approval never. Parse JSONL into a richer internal run-event model, then downsample to Cortex’s existing delta / info / done / error SSE frames.

Persist the Codex thread ID against the Cortex session for resume. On disconnect or timeout, interrupt the process group and save the partial turn without done. This is fast to build, uses the already-authenticated ChatGPT subscription legitimately through Codex itself, and requires no client contract change.

Why Codex first? Its local CLI supplies OS-enforced sandbox modes. OpenCode’s permission rules are useful policy, but they are not a host sandbox and most actions default to allow.

Non-negotiables

  • Never copy or parse either CLI’s credential file.
  • Never accept a raw working directory from /listen.
  • Never run two mutating engines in the same workspace concurrently.
  • Never use --yolo or OpenCode --auto as a product default.
  • Never label the experience “agents” in the public API or UI.

The screen-control plane is a later native macOS capability, not a CLI flag.

A shipped macOS precedent

HeyClicky 1.0.42 demonstrates the same separation this report recommends: a managed Codex runtime orchestrates a distinct native computer-use helper through local MCP.

observed / 03

Observed in the installed, signed app bundle

Codex is the reasoning runtime. The macOS helper owns the hands and eyes.

/Applications/HeyClicky.app identifies itself as version 1.0.42 (build 51). Its Sparkle feed dates that release to 20 July 2026. The bundle contains an architecture-selecting Codex launcher, architecture-specific Codex binaries, and a separate universal native executable named ClickyComputerUseRuntime.

The bundled, product-managed cua-driver documentation says Codex spawns that helper as a local computer-use MCP server backed by Cua. The helper inherits the app’s Accessibility and Screen Recording grants. The required loop is snapshot → element-scoped action → re-snapshot and verify.

Capability restraint is part of the design. The helper may contain upstream recording support, but the shipped instruction and tool surface explicitly hide recording/replay, coordinate-only clicks, cursor movement, drag and zoom in this release.

What this changes

The proposed “native macOS host” is no longer just conceptual. A credible Cortex direction is:

  1. Bundle/pin an execution runtime.
  2. Ship a signed native capability helper.
  3. Expose a curated local MCP surface.
  4. Give the assistant policy instructions for its use.
  5. Keep unavailable upstream tools truly unregistered.

Evidence, not extrapolation

  • CodexRuntime/bin/codex selects aarch64-apple-darwin or x86_64-apple-darwin, prepends bundled rg, then execs the vendor Codex binary.
  • .clicky-codex-version records Codex 0.132.0 and a content hash.
  • ClickyComputerUseRuntime is a universal arm64/x86_64 Mach-O helper.
  • The signed app identity is com.humansongs.clicky; the product docs require Accessibility and Screen Recording.
  • The visual cursor overlay is documented as enabled by default and is rendered by an AppKit runloop in the helper.
  • The current callable loop excludes trajectory recording/replay even though RECORDING.md describes upstream support.
Inference for Cortex

Pattern to adopt, claims to re-test

  • Cortex can keep one visible assistant while Codex privately invokes a computer-use capability through MCP.
  • A signed native host should own TCC checks, capture/action lifecycle, capability registration and a visible progress overlay.
  • Tool registration—not prompt wording alone—should enforce the safe subset. Hidden recording/replay is a useful precedent for least capability.
  • The same helper could eventually be mediated for OpenCode because OpenCode supports MCP, but interoperability is not proven by the HeyClicky bundle.
  • HeyClicky’s permission inheritance, background-event behavior, Cua licensing, code-signing setup and focus guarantees must be independently validated for a Cortex bundle.

Use ordinary subprocess pipes

JSONL is designed for stdout. A PTY adds terminal escape handling, resize state and ambiguous prompts; reserve PTY use for one-time interactive login/TUI diagnostics outside request handling.

Limitation

A non-interactive run cannot wait for a person to answer a fresh approval prompt. With approval=never, blocked work fails cleanly. Rich approvals require app-server/SDK or a new client affordance.

Destination

Codex app-server or Python SDK

Officially intended for deep product integrations requiring authentication, conversation history, approvals, cancellation and streamed events. The app-server speaks bidirectional JSON-RPC over stdio; the beta Python SDK controls that app-server and bundles a pinned runtime.

Where it meets Cortex

Concrete seams in the current dirty working tree, with no assumption that experimental code is already production-ready.

repo / 05
Keep

HTTP and session lifecycle

  • controller.py:82–98 already creates/reuses the session and exposes X-Session-ID.
  • service.py:135–178 already inserts heartbeats and cancels the producer when streaming ends.
  • conversation_ent.py:84–104 serializes one session in one process.
  • pipeline_llm.py:151–182 already saves partial ordered parts in a shielded finalizer.
Change later

Execution semantics

  • Provider is a literal of OpenAI/Gemini/Anthropic, and the current loop is sequential text/provider streaming.
  • Project has a name but no trusted workspace root.
  • The session lock is in-memory only; it does not protect a directory across workers or sessions.
  • Current chunks cannot represent a pending approval or lifecycle terminal reason precisely.

No-frontend-change route

  1. Keep the incoming providers token as a presentation lane. A server-side personal execution profile decides whether that lane uses the current cloud adapter or a local execution engine.
  2. Do not add codex, opencode, “agent,” “subagent,” or execution-session IDs to the public request/response yet.
  3. Route one configured lane through WorkRuntime.run(...). Emit the original lane name in current SSE so the existing client continues rendering it.
  4. Reject a request that would start multiple mutating executors. Existing multi-provider sequential fan-out is safe for read-only model calls, not for two engines editing the same checkout.
  5. Persist upstream continuation IDs privately. The existing provider_response_id could carry an MVP thread/session ID, but a later rename to continuation_id or a dedicated run record is clearer.
Do not infer “act” from prompt text in v1. Select execution through a server-side personal profile or explicit trusted configuration. Intent classification can be added only after false-positive side effects have a safe approval surface.

Workspace lease

Resolve project → immutable canonical root. Acquire a Redis lock keyed by root for mutating runs; the existing session lock remains useful but is insufficient across different sessions or Uvicorn workers.

Process hygiene

Use create_subprocess_exec, never a shell string. Drain stdout/stderr concurrently. Spawn a process group. Apply idle and total deadlines. Cap event and line sizes.

Environment

Allowlist HOME, PATH, locale and engine-specific variables. Do not inherit the FastAPI process’s database, JWT, cloud, or provider secrets into a child that runs repository code.

Cancellation

First call engine-native abort when available; then SIGINT, short grace, SIGTERM and SIGKILL on the process group. Persist partial output without done.

Telemetry

Record run ID, Cortex session/turn, engine/version, policy hash, workspace reference, upstream ID, latency, exit cause and usage. Redact prompts, raw command output and absolute home paths by default.

Startup health

Check executable path/version and safe auth status commands only. Fail closed if the engine, login or configured root is unavailable. Never inspect the credential value.

The screen is a separate capability plane—with a real precedent

Codex and OpenCode can accept screenshots (codex exec --image; opencode run --file), but neither automatically grants Cortex continuous macOS vision or safe desktop control. The eventual single-entity assistant needs a native local host that owns:

Perception

Screen Recording permission, window metadata, redaction, capture cadence and attachment lifecycle.

Action

Accessibility permission, semantic action API, dangerous-action classification, foreground-app checks and rollback where possible.

Authority

User-visible approval for purchases, sends, deletion and credential access. Provider output is a proposal, never the authority boundary.

This host should speak the same internal RunEvent/ActionRequest protocol. HeyClicky 1.0.42 demonstrates one viable packaging pattern—Codex plus a native Cua-backed local MCP helper—while Cortex must independently validate signing, TCC behavior, safe tool selection and background interaction. The product remains one assistant even when implementation capabilities are modular.

Blocked assumptions & risks

The main blockers are product authority and workspace identity—not whether a subprocess can be started.

risk / 07
High

No project → filesystem-root contract

Current Projects have only name and timestamps. An execution engine needs one canonical, immutable, allowlisted workspace root before the first turn.

Block Stage 1 mutation
High

No interactive approval surface

The current SSE schema can report info/error but cannot pause and collect an approval. MVP must use deterministic predeclared allow/deny policy and fail blocked actions.

Defer rich approvals
High

OpenCode permissions are not containment

Most permissions default to allow, and rule matching lives inside the tool. Run mutating OpenCode tasks inside an external isolation boundary.

Security design
High

Environment-secret inheritance

The FastAPI process holds Mongo, Redis, JWT and cloud secrets. A naive subprocess inherits them, and repository code can print or exfiltrate them.

Allowlist child env
Medium

Subscription portability is engine-specific

Codex may reuse Codex’s ChatGPT login. OpenCode may reuse OpenCode’s own documented login or Go key. There is no supported reason to move a token from one store to the other.

Separate health checks
Medium

OpenCode third-party OAuth support can drift

OpenCode documents ChatGPT Plus/Pro login today, but OpenAI’s Codex docs do not promise interoperability with unrelated clients. Treat it as an OpenCode-supported path, pin versions, and keep API-key/Go fallbacks.

Compatibility watch
Medium

Process-local session locking

The current lock protects only one session in one Python process. Different sessions can still edit the same directory; multiple workers do not share the lock.

Redis workspace lease
Medium

Upstream history can diverge

Cortex Mongo history and engine-native thread/session history are separate sources. Pin a continuation to a workspace and engine version; fall back to a fresh run with normalized history when resume fails.

Continuation policy
Medium

Dirty tree and multi-engine edits

This checkout is already heavily modified. Execution adapters must preserve user changes, detect overlapping work, and avoid multi-engine mutation fan-out.

Preflight + lease
Medium

A precedent is not a reusable entitlement

HeyClicky demonstrates a bundled helper/MCP pattern, but Cortex must validate its own code signing, TCC attribution, helper lifecycle, Cua licensing and focus behavior. Do not copy private binaries or assume identical permission inheritance.

Native spike + counsel
Medium

AGENTS.md absent in Cortex

No AGENTS.md exists in this checkout. The only nearby file is ../cortex-app/AGENTS.md, which does not govern backend code. Future target projects may have their own applicable guidance.
